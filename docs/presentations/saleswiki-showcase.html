сырьё на входе → связанный цитируемый смысл на выходе

Каждый ингест, ресёрч или анализ звонка идёт по одному и тому же циклу: источник сохраняется неизменным, из него извлекаются сущности, обновляется карточка знаний, ставятся перекрёстные ссылки, перестраиваются индексы и фиксируется след в трекинге. Ничего не теряется, каждый факт — со ссылкой на источник.

Анатомия карточки — четыре зоны governance
единые обязательные секции на каждый тип · разделение защищённого и рабочего
🔒Controlled Profileзащищённое ядро идентичности; меняется только через review (profile_lock).
✏️Live Intelligenceрабочая область: сюда ложатся ресёрч, мониторинг и анализ.
⏳Review Neededочередь предложенных правок — ждёт одобрения куратора.
📜Change Historyаудит-след: кто, что и когда изменил, с источником.
YAML-properties вверху (атомарные: текст, числа, даты, списки, ссылки) + длинные пояснения и evidence — в теле. Свежесть отслеживается по типам (профиль 30 дн., hot-лиды 3 дня и т.д.).

Properties — YAML frontmatter (атомарные: текст, числа, даты, списки, ссылки)
--- entity_id: company_01J8… 🔒 # минтуется один раз через new_entity.py type: company template_version: 2 created: 2026-06-24 updated: 2026-06-24 access: sales-confidential # метка: public…personal-data profile_lock: locked 🔒 freshness: fresh confidence: high owner: … # ABAC: владелец team: … # ABAC: команда ---
Body — обязательные секции (единые на каждый тип)
## 🔒 Controlled Profile # защищённое ядро — меняется только через review ## ✏️ Live Intelligence # рабочая область: ресёрч, мониторинг, анализ ## ⏳ Review Needed # очередь предложенных правок — ждёт approve ## 📜 Change History # аудит-след: кто/что/когда + источник
Правило: свойства атомарны и машиночитаемы, длинные пояснения и evidence — в теле. Health-check проверяет, что обязательные секции и enum-значения на месте, а boundary совпадает с папкой карточки.

Закрытость — как обеспечивается

  • Controlled Profile отделён от Live Intelligence — защищённое ядро не смешано с рабочей зоной
  • profile_lock уважается; непустые controlled-поля не перезаписываются без явного approval, доверенного sync или ревью куратора
  • Граница = папка, не метка — доступ определяется физическим расположением, fail-closed для неизвестных путей
  • Метки доступа — public · internal · sales-confidential · personal-data · legal-review
  • Permissioned-шлюз — can_read до любого вывода; приватное только как непрозрачный handle; чувствительное не копируется в широкие summary

Неизменяемость — как обеспечивается

  • raw/ неизменно — источники не переписываются; ошибка фиксируется отдельной correction-заметкой со ссылкой на оба
  • Карточки не удаляются в обычном ресёрче — только архив или merge-дубликатов
  • entity_id выдаётся один раз через единый chokepoint; append-only id-ledger.jsonl
  • Правки идут в Review Needed → approve → single-writer worker применяет транзакционно (revert-on-failure, dead-letter, rollback)
  • Change History + tamper-evident audit-цепочка + git — каждое изменение прослеживаемо; health-check ловит дрейф

03

Доступ по ролям, без утечек

граница = физическое расположение · по умолчанию fail-closed

Permissioned-сервис (saleswiki_mcp/) на один и тот же вопрос даёт разной роли разный безопасный ответ. Доступ определяется папкой, в которой лежит карточка, а не YAML-меткой; карточка вне известных границ попадает в quarantine и не видна никому.

Гарантии no-leak

  • Fail-closed по умолчанию — неизвестная граница = блок, не «broad»
  • can_read до вывода — тело карточки эмитится только при allow
  • Extract-only — ответы из цитируемых данных, без генерации/галлюцинаций
  • ABAC owner/team — AE видит только свои/командные сделки
  • Tamper-evident audit — хеш-цепочка, race-safe запись
  • Handle-only PII — сырые транскрипты в personal-data запрещены и проверяются health-check

9 ролей доступа

  • employee · SDR · marketing — общие карточки, без цен/ACV
  • account-exec — свои/командные сделки (ABAC)
  • head-of-sales · revenue-ops — все сделки
  • legal-reviewer — общая + legal-review
  • curator / admin — review/approve; personal-data только admin
Доступ по запросу — живые гранты. Роль без доступа может запросить его: одобрение выдаёт scoped-грант на одну компанию с TTL (по умолчанию 30 дней, аппрувер задаёт свой), который переживает применение других правок, отзывается одной командой и гаснет по сроку — битый срок гасит грант (fail-closed), а не делает вечным. Personal-data открывает только одобрение админа.
04

Конфигурируемость без кода

поведение задаётся JSON-контрактами, валидируется health-check

Роли, границы, владение, источники полей ответа, scoring и коннекторы — это редактирование JSON в schemas/, а не правка кода. Под другой по форме vault можно подложить иной профиль извлечения полей — без изменения шлюза.

access-policy.json

Роли, границы, ABAC-ограничения, роли approver/reviewer.

boundary-registry.json

Папка → граница доступа; fail-closed дефолт (quarantine).

identity-provider.json

Пользователи, маппинг ролей, org-реестр валидных владельцев/команд.

field-extraction.json

Какую секцию/метку читает каждое поле ответа — отвязка от формы карточки.

scoring-models.json

Веса, бэнды, штрафы и действия скоринга лидов/сделок.

connector / agent / event

Контракты коннекторов, маршрутизация агентов, профиль event-ресёрча.

Секреты — только имена env-переменных. Ключи HubSpot/Webwright/OIDC никогда не лежат в репозитории; нет ключа — стадия мягко пропускается. Все 9 контрактов проверяются health_check.py.

Глоссарий — простыми словами

если встретили незнакомый термин выше
База знаний Obsidian-vault
Папка со связанными Markdown-заметками. Открывается в бесплатном Obsidian как личная «вики» с графом связей.
Карточка / сущность
Одна типизированная заметка (компания, сделка, звонок…) с обязательными секциями и YAML-свойствами.
Controlled Profile
Защищённое ядро карточки. Меняется только через ревью; обычный ресёрч его не перезаписывает.
Граница доступа boundary
Папка определяет, кому видна карточка. Неизвестная папка = карантин (никому), а не «всем».
RBAC + ABAC
Роль задаёт доступные границы; атрибуты (владелец/команда) сужают доступ к конфиденциальным сделкам.
No-leak / fail-closed
При любой неопределённости система скорее закроет доступ, чем покажет лишнее. Приватное — как непрозрачный handle.
MCP-шлюз
Сервер, через который ИИ-клиент задаёт ролевые вопросы к vault. Роль определяет сервер, не клиент.
Чат-бридж Rocket.Chat
Мост: сотрудник спрашивает в чате обычными словами и получает ролевой ответ, без установки клиента.
Governance-петля
Правка проходит путь предложение → ревью → одобрение → применение, с возможностью отката.
Single-writer worker
Единственный процесс, который пишет в карточки — транзакционно, с откатом и очередью «мёртвых писем».
Грант доступа access grant
Одобренный запрос доступа: временное (TTL) право одной роли читать закрытые данные одной компании. Отзывается командой, гаснет по сроку.
Answer Contract
Формат ответа: вывод → цитируемые факты → свежесть → следующий шаг. Без выдумок; нет данных — честный not-found.
ADR
Запись архитектурного решения: контекст, выбор, последствия, отвергнутые альтернативы.
Курируемая база знаний о продажах, которая отвечает каждому по его роли — без утечек приватного и без выдуманных фактов.
